# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A tiny, clean playground for building audio-reactive visuals, sized around a small TFT screen so effects will port to a microcontroller later. It renders to a logical canvas and scales it up to a desktop window via pygame.

## Setup and running

```bash
python -m venv .venv && source .venv/bin/activate   # optional but recommended
pip install -r requirements.txt
```

`sounddevice` needs PortAudio under the hood (macOS: `brew install portaudio`, Debian/Ubuntu: `sudo apt install libportaudio2`). If it's missing, resting mode still works — `sounddevice`/`soundfile` are imported lazily in `audio.py`.

```bash
python run.py                             # resting/idle mode — no audio hardware needed
python run.py --source mic                # microphone (default input device)
python run.py --source line --device 2    # line-in / a specific input
python run.py --source wav --wav song.wav # play + react to a wav file, in sync
python run.py --source loopback --spotify # react to Spotify + use its album art
python run.py --source loopback --switch-output=none  # don't borrow the system output
python run.py --list-devices              # find your input device index
python nowplaying.py                      # print current Spotify track + palette
python run.py --leds udp://audioviz.local:4210 --led-count 60  # drive an LED strip
python run.py --leds udp://audioviz.local:4210 --led-count 1   # analog 12V RGB strip
python tools/led_monitor.py               # fake LED strip in the terminal (testing)
python tools/find_leds.py                 # find the strip on the network + test it
python run.py --leds udp://audioviz.local:4210 --led-profile mine.json  # a named LED profile
python tools/analyze_wav.py song.wav      # measure the loudness pipeline, no playback
```

`--wav` accepts a bare filename and looks it up in `AudioFiles/` (created next
to `run.py`) if it isn't found as given — drop files there instead of typing
full paths. `AudioFiles/` is gitignored, so your music never ends up in git
history.

Spotify (`--spotify`) supplies **album art and colors only** — its API does not
expose the audio stream, and its Audio Analysis/Features endpoints were
deprecated for new apps in Nov 2024. Reactivity always comes from `--source`,
so pair `--spotify` with `--source loopback` (BlackHole; see README) or
`--source mic`. `--source loopback` falls back to the mic when no loopback
device is present.

There is no test suite, linter, or build step in this repo. Verify changes by running the app and watching the debug HUD (`h` key) — it shows fps, source, scene, and live rms/bass/mid/treble/centroid readouts, plus a beat indicator dot.

Controls: `1`-`9` switch scene, `h` toggles HUD, `l` toggles the LED tuning panel, `f` toggles fullscreen, `esc` leaves fullscreen (or quits when windowed).

## Architecture

Data flow is a strict one-way pipeline:

```
audio source  →  FeatureExtractor  →  Features ─┬─→  Scene.draw()  →  canvas → window
(mic/line/wav/resting/loopback)      (the contract)  ↑
                                                │    │
Spotify  →  NowPlayingProvider  →  NowPlaying  ─│────┘
(metadata)  (background thread)    (art + palette, via Scene.now_playing)
                                                │
                                                └─→  Scene.led(f) → LedSink → ESP32 → strip
                                                     (led.py, background thread)
                                                          ↑
                                          LedProfile (ledprofile.py, the `l` panel)
```

The two inputs are independent: audio drives motion, Spotify drives color and
imagery. `Features` stays audio-only on purpose (it's the MCU-portable
contract), so album art rides the separate `Scene.now_playing` channel.

- **`features.py`** — the core reusable logic, meant to be the part eventually reimplemented on an MCU. `Features` (dataclass) is the universal contract every scene consumes: `rms`, `bass`, `mid`, `treble`, `centroid` (all 0..1, smoothed + auto-gained), `bands` (a 24-bin log-spaced 20Hz-21kHz spectrum for bar-style visualizers, same smoothing/auto-gain treatment, auto-gained *per bin* so the top bins stay visible at all), plus `beat`/`beat_strength`/`t`. `FeatureExtractor` does FFT band analysis, auto-gain, an attack/release envelope follower, and simple energy-based beat detection on the bass band. **The auto-gain is where loudness dynamics live or die.** It is a slow reference (`REF_RISE_S`/`REF_FALL_S`, plus a brief `REF_WARMUP_S` fast-settle so a new source calibrates in a moment) with a fixed dB window below it (`RANGE_DB`, `HEADROOM_DB`) and a soft knee at both ends (`KNEE`). The split is deliberate: the reference absorbs *input gain*, which differs by tens of dB between a mic, a line-in and a loopback, while the window maps *musical dynamics*, which is what the visuals exist to show. The previous instant-attack running max conflated the two and flattened section-to-section contrast — a drop read only 0.08 above the buildup before it on a 0..1 scale. `RANGE_DB` is the knob to reach for, and it has to stay matched to how little dynamic range modern masters use: measured on real tracks, 4s-smoothed level moves only ~1.5-5 dB from a loud section to the loudest one, so a wide window buries that difference and a narrow one parks half the frames on the floor. Never tune it by eye — `tools/analyze_wav.py` exists for exactly this. `push()` is called from the audio callback thread; `read()` is called once per frame from the render thread — the two are separated by a lock. Tuning knobs (`FFT_SIZE`, `BANDS`, `N_SPECTRUM_BINS`/`SPECTRUM_RANGE_HZ`, `ATTACK`/`RELEASE`, the auto-gain constants above, `BEAT_SENSITIVITY`/`BEAT_FLOOR`/`BEAT_REFRACTORY`) live as class constants at the top. `BANDS` puts bass at 20-120Hz rather than the obvious 20-250: on a limited master the difference between a buildup and a drop is almost entirely sub-bass, and 120-250Hz outvotes it inside a band mean — narrowing it roughly doubled a drop's lift on `f.bass`. The class holds no wall clock; `t` and the beat refractory run on accumulated `dt`, which is what lets the analysis tool push a track through faster than realtime.
- **`audio.py`** — three interchangeable sources, all exposing `start()` / `read(dt) -> Features` / `stop()`: `LiveAudioSource` (mic/line-in/loopback, same code path, device index picks the input), `WavSource` (plays a wav out loud and analyzes the same audio in the output callback so visuals stay locked to what's heard; loops forever), and `RestingSource` (no hardware — synthesizes idle motion from incommensurate LFOs so scenes work unchanged with zero setup; its fake spectrum is sized from `N_SPECTRUM_BINS` and built as two waves travelling along the bin axis, so neighbouring bins stay correlated and it reads as a spectrum rather than as noise). Also `resolve_wav()` (the `AudioFiles/` lookup behind a bare `--wav` name; it lives here rather than in `run.py` so headless tools can reuse it without pulling pygame in) and `find_loopback_device()`, which scans for BlackHole/Soundflower-style virtual inputs so `--source loopback` can capture system output. `sounddevice`/`soundfile` are imported in `try`/`except` so `RestingSource` works without the audio stack installed.
- **`nowplaying.py`** — the second input, parallel to and independent of the audio pipeline. `NowPlaying` (dataclass: `track_id`, `title`, `artist`, `art` Surface, `palette`, `accent`) is what scenes read off `self.now_playing`. Two interchangeable backends both exposing `poll()`: `AppleScriptBackend` (local Spotify desktop app, zero setup, macOS-only — and it checks System Events first so polling never *launches* Spotify) and `WebAPIBackend` (OAuth PKCE, cross-platform, needs `SPOTIFY_CLIENT_ID`). `NowPlayingProvider` polls on a daemon thread and downloads/analyzes art there; `read()` is a lock-guarded snapshot the render thread calls per frame and never blocks on I/O — the same split `FeatureExtractor` uses, and for the same real-time reason. All backend errors are swallowed so a Spotify hiccup can't take down the render loop.
- **`scene.py`** — the `Scene` interface: `update(f, dt)` advances animation state, `draw(surface)` does pure rendering onto the logical canvas, `SUPERSAMPLE` declares how much SSAA this scene needs (pygame rect/polygon drawing has no AA, so hard-edged scenes want 2 and smooth/expensive ones want 1 — Nebula at 2 costs 93ms), and the optional `led(f)` returns an LED frame (any length; `None` to accept `led.default_led`). Scenes must *not* add their own beat flash to `led()` — `LedSink` pulses every frame. Also the `now_playing = None` class-attribute default that `App` fills in each frame. Keeping these separate makes scenes swappable.
- **`fx.py`** — shared rendering/math helpers scenes compose instead of re-deriving. `draw_field`'s `field_fn` may return `(hue, value)` or `(hue, value, sat)`, the latter letting a palette own its own saturation. Color/scale helpers (`hsv`, `hsv_array` — the vectorized counterpart, any shape, so one call colorizes a 2-D field or a 1-D LED strip — `scale`, `aacircle`, `fade`, `scratch_surface`), a vectorized `Particles` system, lightning-bolt geometry, procedural field rendering (`field_grid`/`draw_field`), album-art helpers (`palette_from_surface` k-means color extraction, `most_vivid`, `circle_masked`, `blurred_backdrop`), and the 3D point-cloud stack. Check here before building a new visual primitive.
  - The 3D stack is what every scene in the Constellation family is built from, so those scenes are only a *projection*: `SpectrumHistory` (the "Z is time" ring buffer — fixed-rate `np.roll` pushes plus a fractional `.acc` so the field drifts continuously instead of stepping once per row, and the `np.interp` upsample from the 6 coarse `f.bands` to N smooth columns), `perspective`/`depth_tail` (the camera and the row fade that dissolves the horizon), and `PointCloud`. `PointCloud.splat(surface, px, py, sigma, rgb, ambient, glow)` takes normalized 0..1 screen coords, a per-point Gaussian radius in *buffer* pixels and per-point RGB with intensity already multiplied in (accumulation is additive, so brightness lives in the color, not an alpha), scatters them all into one float buffer sized to the canvas but capped by `max_px` (so at 1080p it is near 1:1 and a far point stays a crisp pixel), then adds a blurred copy of that buffer back on top for glow. `ambient` is a constant wash added *into* the buffer rather than blitted over the canvas, because a full-canvas `BLEND_ADD` fill costs ~7ms at 1080p — and the glow pass re-adds it, so what lands on screen is about `(1 + glow)x` the value passed.
  - Five things in `PointCloud` are load-bearing and easy to undo by accident: the Gaussian is **peak**-normalized, not area-normalized (area normalization spreads a near dot's light thinner the bigger it gets and washes the front rows out); the whole kernel goes through **one** scatter over a `(taps, N)` block rather than one call per tap (4x); that scatter uses `np.bincount`, not `np.add.at` (2.7x); `px - xi.astype(np.float32)` is deliberate, because `float32 - int32` promotes to **float64** under numpy's rules and silently made every downstream array double-width (5x); and the glow gain is a `BLEND_MULT` fill on the *small* blurred surface, since the same fill at 1920x1080 costs ~7ms by itself.
- **`scenes.py`** — `PulseScene` (breathing orb — radius from bass+rms, beat triggers expanding rings; colors from `SPECTRUM_COLOR_SCHEMES` like the other scenes, with two independent Spotify switches, `USE_ALBUM_ART` for whether the cover *becomes* the orb and `USE_ALBUM_COLORS` for whether the palette overrides `COLOR_SCHEME`), `SpectrumScene` (one bar per `f.bands` bin, growing symmetrically up/down from a center line, Apple-Music-style), `CymaticsScene` (nodal standing-wave interference patterns, one mode per band), and the six-scene 3D family below. `BarsScene` (the "is the pipeline alive" diagnostic view), `LightningScene` (beat-triggered branching bolts) and `NebulaScene` (drifting glow-particle field) are still defined here but no longer in `run.py`'s list — there are only nine number keys; swap one back in if you want it.
  - **The 3D family.** `ConstellationScene` (X=frequency, Y=level, Z=time, so each older spectrum drifts back toward a vanishing point — legible across a room like `SpectrumScene` while moving organically like `CymaticsScene`), `ChasmScene` (Constellation mirrored about the horizon into a corridor, the lower half dimmed and blurred by `REFLECT_DIM`/`REFLECT_BLUR` so it reads as a reflection rather than a second wall — it is *only* an overridden `_project()`), `VortexScene` (the same history as rings receding down a tunnel: frequency is the angle, level bulges the wall out, `TWIST` corkscrews it and a beat both flares the wall and dollies the camera forward), `ResonanceScene` (Cymatics in 3D — a golden-angle sphere of ~6k points displaced by the same per-band standing-wave sum, split into `_field()`/`_colorize()` so `led()` samples the equator of the very same field), `CartographScene` (the history as hidden-line ridgelines, an animated *Unknown Pleasures* plot — each row is filled with the background color before its top edge is stroked, and that fill **is** the occlusion; the only scene in the family that doesn't splat, hence `SUPERSAMPLE = 2`), and `LatticeScene` (a fixed 3D grid with three band-driven plane waves sweeping through it while the camera orbits; `FAINT` keeps the unlit scaffolding visible, which is why this is the one scene with something on screen during a quiet passage).
  - They share one substrate — `fx.SpectrumHistory`, `fx.PointCloud`, `fx.perspective` and the `SpectrumColored` mixin — so a new one is a projection, not a renderer: compute `px`/`py`/`sigma`/`rgb` and hand them to the cloud. All land around 12-14ms/frame at 1080p. Tune by subclassing, not by mutating an instance: `__init__` precomputes geometry from `NX`/`NZ`/`N_POINTS`.
  - `SpectrumColored` is the shared palette plumbing every scene coloring itself out of `SPECTRUM_COLOR_SCHEMES` mixes in *ahead of* `Scene`: `COLOR_SCHEME`/`USE_ALBUM_COLORS`, the `_active_color_fn()` album-override rule, the standard `_spectrum_led()` body, and `_scheme_lut()`. That last one matters for `ResonanceScene`/`LatticeScene`: Constellation can afford ~100 Python calls to a scheme function per frame, ~6000-point scenes cannot, so they sample the scheme into a 64-entry RGB table once a frame and `np.take` from it. Index-based schemes (`blue_pink`, `rainbow`) make hue encode frequency and read best in Constellation/Vortex; level-based ones (`me1`, `fire`) color by loudness, which is what Resonance and Lattice want.
  - `PulseScene.led`, `SpectrumScene.led` and `CymaticsScene.led` reuse the scene's own colors so screen and strip never diverge; `SpectrumColored._active_color_fn(np_)` is shared by `draw()` and `led()` in every scene that mixes it in, and is the single place the album-vs-`COLOR_SCHEME` choice is made. `CymaticsScene` does it by splitting the pattern into `_field()` (the math) and `_colorize()` (every look dial), so `led()` evaluates the *same* field along a horizontal line through the canvas centre — the strip is a slice of what's on screen. A scene with no `led()` falls through to `led.default_led`, whose hue is the raw unsmoothed `f.centroid`; that reads as random next to any scene with an actual palette, so any scene with one should define `led()`.
  - `CymaticsScene` color is pluggable the same way: `CYMATICS_COLOR_SCHEMES` maps a name to a `(field, centroid, t, np_) -> (hue_array, sat)` function, `COLOR_SCHEME` picks one, and `USE_ALBUM_COLORS` overrides with `album` while a track plays. The registry also carries a mirrored `spectrum:<name>` entry for every `SPECTRUM_COLOR_SCHEMES` palette (built by `_make_cymatics_spectrum_mirror`, which samples the RGB scheme into a hue LUT and looks the field up in it), so Cymatics, `SpectrumScene` and `ConstellationScene` can share one set of colors -- the default is `spectrum:me2`. Adding a spectrum scheme gets you the cymatics version for free. Note `field` grows with loudness (roughly ±0.5 quiet, ±3.5 on a loud beat), so a scheme that multiplies it straight into hue spreads more of the color wheel the louder it gets — the calm schemes pass it through `np.tanh` first to cap the spread. The field is computed at reduced resolution and upscaled; `FIELD_MAX_PX` is a pixel *budget* rather than a fixed divisor, so frame time stays flat as the canvas grows (~500x330 at 1512p, ~550x310 at 4K) instead of the old fixed 240x135 that became an 8-16x upscale. Separate dials for intensity: `SATURATION`, `CONTRAST` (gamma on brightness; >1 carves dark space out of an otherwise uniformly-lit canvas), `BRIGHTNESS`, `MOTION` (scales the scene clock), and `CENTROID_SMOOTHING` (`f.centroid` is the one Feature *not* smoothed by the envelope follower, so raw it makes colors buzz).
  - `PulseScene` samples that same registry at `COLOR_ROLES` (3) evenly spaced points for its glow/core/ring, with the level being the bass+rms mix that drives the radius — so an index-based scheme gives the three roles distinct hues while a level-based one moves one hue with the orb's breathing. `_colors()` is the single place, shared by `draw()` and `led()`. The background is the glow color scaled by `BACKGROUND_TINT`. `USE_ALBUM_ART` and `USE_ALBUM_COLORS` are deliberately separate so "cover art, but my colors" and "my own disc, tinted by the album" are both reachable.
  - `SpectrumScene` color is pluggable: `SPECTRUM_COLOR_SCHEMES` maps a name to a `(i, n, val, f, np_) -> (r, g, b)` function, and `COLOR_SCHEME` picks one. Two schemes exist for scenes with no bar index: `drift` (a slow ~3-minute fade around the whole wheel — nothing steps, everything fades) and `centroid` (hue from spectral brightness, the look `PulseScene` and `led.default_led` have always had). A scheme added here reaches `SpectrumScene`, `ConstellationScene`, `PulseScene` *and* `CymaticsScene` (as `spectrum:<name>`) at once. `USE_ALBUM_COLORS` overrides that with the `album` scheme whenever a track is playing -- note every scene currently ships with it (and `PulseScene.USE_ALBUM_ART`) set to `False`, so `--spotify` changes nothing on screen until you flip one; `BAR_WIDTH_FRAC` sets bar width without moving bin centers. Add a scheme by writing the function and listing it in the registry.
- **`led.py`** — the second *output*, exactly parallel to the canvas branch (as `nowplaying.py` is the second *input*). `LedSink.submit(pixels, f)` is a non-blocking handoff from the render thread; a daemon thread does `resample → smooth → beat pulse → floor → brightness → gamma` and sends frames at `LED_FPS`. `FLOOR`/`_lift` is the "minimize black" rule for *every* scene: a pixel dimmer than `FLOOR` of full output is scaled up to it by a single factor, so its channel ratios — its hue — survive and a quiet moment rests on the scene's own color instead of switching the strip off (with the default schemes, Constellation and Spectrum rest on the palette's light blue). It lives here, not in each `led()`, because gamma is what decides how dark a value actually looks — a scene-side floor of 0.15 lands at 0.15^2.2 = 1.4% of output, i.e. black — hence `_floor_pre`, `FLOOR`'s gamma inverse. It runs after the beat pulse (so beats still pulse up out of the resting glow) and before `brightness` (so `--led-brightness` still dims everything). A pixel that is exactly black has no hue to preserve and is left alone, so a scene whose colors can reach true black lifts its own value first — see `CymaticsScene.LED_FLOOR`. The same lock-guarded-slot split `FeatureExtractor` and `NowPlayingProvider` use, for the same real-time reason. Transports are interchangeable (`UdpTransport` for an ESP32 over WiFi, `SerialTransport` for USB with lazily-imported pyserial, `NullTransport` when `--leds` is off so `App` needs no branch). **Scenes never know the strip length** — they return their natural pixel count and `_resample` maps it onto the hardware, which is what makes an analog 1-color strip and a 300-LED WS2812 the same code path. Smoothing runs *before* the beat pulse deliberately, so the pulse stays sharp. Wire protocol is documented in the module docstring and mirrored in `firmware/*/av_proto.h`.
- **`ledprofile.py`** — the strip's dials, held apart from the visuals on purpose. A scene's `led()` decides *what* the strip shows; `LedProfile` decides *how it lands in the room* (brightness/floor/gamma, gain/contrast/attack/release/beat, scheme/saturation/hue, reverse/mirror/offset), and only the second set changes when the strip moves behind the TV or gets a new diffuser. Three properties are the whole design. It is **global, not per-scene** — the point is tuning the light, so an edit holds across all nine scenes, and `scheme = "scene"` (the default) means "mirror whatever palette the running scene chose", which is what makes a fresh profile a byte-for-byte no-op against the old behavior. It is **live** — `App` mutates it from the render thread while `LedSink` reads it on the sender thread, which is safe because every knob is a plain float/bool/short string, so the worst case is one 16ms frame using the old value; the two caches that can't be read that way (`_gamma_lut`, `_floor_pre`) are rebuilt by `LedSink._refresh_derived()`, which compares a `(gamma, floor)` tuple at the top of each frame rather than taking a callback. And it **persists** to JSON, unknown keys ignored on load, because a strip tuned against your actual wall should stay tuned. `PARAMS` is the single source of truth: the adjust logic *and* the on-screen panel are both generated from it, so a new knob is one entry plus one line of use in `led.py`. The stages themselves (`spatial_map`, `apply_level`, `recolor`) live here rather than in `led.py` so the sink stays the transport/timing layer. Two details in them are load-bearing: `apply_level` scales each pixel by a single factor derived from its *level*, never per-channel, so gain and contrast can never shift a hue (the same argument as `LedSink._lift`); and `recolor` evaluates the chosen `SPECTRUM_COLOR_SCHEMES` function **per pixel** with the real `(i, n, val, f, np_)` — affordable at <=488 pixels on a background thread, and the reason an index-based palette paints a gradient down the strip while a level-based one moves with the music, exactly as they do on screen. A scene's own `LED_FLOOR` (Cymatics 0.3, Resonance/Lattice 0.25) is *not* one of these knobs and stays where it is: it corrects for a scene whose colors can reach true black, which is scene-intrinsic, not taste.
- **`firmware/`** — two ESP32 sketches (`esp32_udp_ws2812` for addressable strips, `esp32_udp_analog` for 12V RGB via MOSFETs) sharing byte-identical copies of `av_proto.h` (the wire format) and `av_net.h` (WiFi/mDNS), duplicated per folder because the Arduino IDE only compiles headers beside the `.ino`. Both fall back to a local breathing animation after `AV_IDLE_TIMEOUT_MS` without frames. `firmware/QUICKSTART.md` is the linear box-to-wall-socket checklist for a new board (toolchain, `wifi_secrets.h`, flashing, the serial-monitor check, the mDNS-vs-IP question, `find_leds.py` once it's on a wall socket) and `firmware/README.md` is the reference behind it — board selection, wiring, addressing, and the troubleshooting table. The split is deliberate: the checklist is read once per board and must not make you choose anything, the reference is read when something is wrong.
  - **Addressing is by name, not IP.** The board stays on DHCP — a wall-powered thing gets unplugged, and the router is free to hand it a new address on every boot — and `av_net.h` advertises a fixed mDNS name (`HOSTNAME`, default `audioviz`) so `--leds udp://audioviz.local:4210` survives that. A static IP was rejected as one more thing to get wrong per network. `avNetBegin`/`avNetLoop` are also why joining is non-blocking: `setup()` never waits on WiFi, so the idle animation runs while the board joins (it routinely boots faster than the router), and `avNetLoop` returns true on the frame the link comes back so the sketch can rebind its UDP socket — the old one is bound to an address the interface no longer holds. `UdpTransport` (led.py) is the other half: it resolves the name off the sender thread and re-checks every 30s, because a *failing* `.local` lookup on macOS blocks for a measured 5 seconds, which is exactly the common case of starting `run.py` before the board is up.
- **`tools/find_leds.py`** — the bring-up check for a board with no serial monitor attached, which is every board once it moves to a wall socket. Waits for `audioviz.local` to resolve (the lookup is slow by nature: a failing `.local` lookup on macOS takes ~5s), pings the address DHCP gave it, then drives R/G/B through the real `LedSink` — so one command covers network, firmware, wiring and channel order, and a wrong color on an analog strip means the gate wires are swapped.
- **`tools/led_monitor.py`** — renders received UDP frames as terminal color blocks, so the whole Python side is testable with no hardware.
- **`tools/analyze_wav.py`** — the measurement harness for the loudness pipeline, and the reason the auto-gain constants are what they are. Reads a file directly (no audio device, no playback), feeds `FeatureExtractor` at the real block cadence and steps `read()` per simulated frame, so a 4-minute track analyzes in seconds. `--compare` runs the pre-dB-window auto-gain alongside (the legacy mapping lives in the tool, not in `features.py`). The metric that matters is **drop** — p95 minus p50 of the 4s-smoothed envelope, i.e. how much a drop lifts above the loud section before it. Per-frame statistics mislead here: **beat** (top 5% vs median) stayed healthy throughout the exact failure where buildups and drops had become indistinguishable, so tune on `drop` and watch `beat` and `floor` only for regressions.
- **`app.py`** — the pygame render loop, and the one piece of interactive UI: the LED panel (`l`), which edits `led_sink.profile` in place — the very object the sender thread reads, so there is no copy to keep in sync. `_draw_hud` splits into `_draw_hud_lines` + `_draw_led_panel` because `h` and `l` toggle independently; the number keys stay live while the panel is open on purpose, since checking one setting across several scenes is the normal way to use it. Owns `CANVAS_W`/`CANVAS_H`/`SCALE`/`FPS` constants (1920x1080 logical canvas, window at `SCALE`=0.5), draws to a fixed-size logical `Surface`, then nearest-neighbour-scales it into the actual window so pixel-art-style effects stay crisp and behave the same at the eventual target resolution. The window is resizable and can go fullscreen (`--fullscreen`, `--display N`, `f` at runtime); `_dest_rect` letterboxes so the canvas aspect is preserved at any window shape, and the HUD font is sized as a fraction of window height so it stays proportional. **Resolution:** `_canvas_for` sizes the canvas to the on-screen rect (so there is normally no canvas→screen resampling at all) times `scene.SUPERSAMPLE * --supersample`, clamped by `MAX_CANVAS_PX`; `--canvas WxH` pins a fixed logical size instead (the MCU-portability mode). All rescaling uses `smoothscale`, never `transform.scale` — the latter point-samples, which destroys an image on the way down (a 1px checker downscaled 2x came out mean 255 instead of 64). Also owns scene switching (number keys) and the debug HUD overlay.
- **`outputswitch.py`** — the macOS system-output borrow behind `--switch-output` (on by default for `--source loopback`). A Multi-Output Device exposes **no master volume**, so while it is selected the volume keys and menu-bar slider are dead and the level is frozen at whatever the speakers were last set to — the recurring "BlackHole is muted" symptom, which is not a routing fault. The fix is to not live on Multi-Output: switch on start, `restore()` on exit via both a `finally` in `run.py` and an `atexit` hook (the second is what covers Ctrl-C and crashes), so the keys come back when the window closes. It shells out to `switchaudio-osx`; everything is a no-op that prints an install hint once when the binary is missing or the target device doesn't exist, which is why `run.py` needs no branch and this can never stop the visuals from starting.
- **`run.py`** — argument parsing (`--source`, `--wav`, `--device`, `--list-devices`, `--switch-output`, `--spotify`, `--spotify-source`, `--leds`/`--led-count`/`--led-brightness`/`--led-profile`), loopback fallback, and the scene registry (order in the `scenes` list maps to number keys 1-9).

## Adding a scene

Subclass `Scene` in `scenes.py`:
